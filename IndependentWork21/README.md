# Самостійна робота №21
## Тема: Інтеграційні тести патернів (підготовка до екзамену).
## Мета: Підготувати інтеграційні тести для рішень із Factory Method / Singleton / Strategy / Observer та перевірити коректну взаємодію твірних та поведінкових патернів у єдиному наскрізному сценарії.

## 1. Початкова ієрархія класів (з порушенням принципів проєктування)

### Опис ієрархії
Було реалізовано монолітний клас `OrderProcessor`, який виконував обробку замовлень та товарів. Вибір типу обробки (наприклад, експрес чи міжнародна доставка) відбувався всередині одного методу через умовні конструкції `if-else`. 
Усі інфраструктурні об'єкти (компоненти сповіщень клієнтів та сховища складу) створювалися безпосередньо всередині методу через оператор `new`.

## 2. Аналіз порушення принципів проєктування
При побудові таких систем без використання шаблонів проєктування виникають критичні архітектурні порушення:

- **Порушення Open-Closed Principle (OCP):** Будь-яка зміна або додавання нового типу обробки замовлення змушує модифікувати вже існуючий відтестований код класу `OrderProcessor`.
- **Порушення єдиного стану (Загроза для Singleton):** Створення об'єктів складу через `new InventoryStore()` у різних частинах програми призводить до втрати актуальності даних та розсинхронізації лічильників і залишків товарів.
- **Жорстка зв'язаність (Tight Coupling / Порушення DIP):** Клас обробника безпосередньо залежить від конкретних реалізацій сервісів (наприклад, `SmsNotification`), що унеможливлює ізольоване тестування логіки без виклику реальної інфраструктури.

Таким чином, монолітна структура робить код крихким, а його розширення та підтримку — надзвичайно складними.

## 3. Альтернативне рішення з використанням патернів
**Обраний підхід**

Було обрано підхід повної декомпозиції системи за допомогою комбінації твірних патернів (**Factory Method**, **Singleton**) та поведінкових патернів (**Strategy**, **Observer**) для ізоляції алгоритмів та переведення взаємодії модулів на подієву модель.

## 4. Нова структура класів
**Опис:**

`IProcessingStrategy` — інтерфейс, що стандартизує контракт для різних алгоритмів обробки замовлень.

`RegularStrategy`, `ExpressStrategy`, `InternationalStrategy` — конкретні реалізації стратегій (патерн *Strategy*).

`StrategyFactory` — фабричний метод, що приховує логіку вибору та ініціалізації необхідної стратегії за рядковим типом (патерн *Factory Method*).

`OrderManager` — центральний координатор системи та лічильник замовлень, захищений від дублювання (патерн *Singleton*).

`OrderContext` — контекст виконання, який викликає стратегії та містить події (events) для сповіщення зовнішніх підсистем.

`InventoryObserver`, `NotificationObserver` — незалежні класи-слухачі, які автоматично реагують на події успішної обробки (патерн *Observer* через події C#).

## 5. Коректна робота клієнтського коду та тести
Клієнтський код тепер повністю ізольований від деталей створення об'єктів та логіки алгоритмів, оперуючи виключно абстракціями. 

**Результати інтеграційних тестів (xUnit):**
Написано та успішно пройдено 5 наскрізних інтеграційних сценаріїв для перевірки взаємодії патернів:
- `FullIntegration_ShouldProcessRegularOrder_AndNotifyObservers` — позитивний сценарій: фабрика створює правильну стратегію, контекст її виконує, а всі обсерватори успішно отримують актуальні дані.
- `SingletonState_ShouldMaintainConsistency_AcrossMultipleContexts` — позитивний сценарій: підтверджено, що `OrderManager` надійно зберігає стабільний єдиний стан незалежно від кількості створених контекстів.
- `RuntimeStrategySwitch_ShouldChangeBehaviorDynamically` — позитивний сценарій: підтверджено можливість динамічної зміни стратегії обробки безпосередньо в рантаймі.
- `FactoryMethod_ShouldThrowException_WhenStrategyTypeIsUnknown` — негативний сценарій: перевіряє стійкість системи та генерацію винятку при спробі передати неіснуючий тип стратегії.
- `ContextExecution_ShouldNotFail_WhenObserversListIsEmpty` — граничний сценарій: гарантує стабільну роботу та успішне завершення обробки навіть за повної відсутності підписників (нульова кількість спостерігачів).

## Висновок
- Поєднання Creational та Behavioral патернів дозволило побудувати повністю розширювану структуру додатка.
- Патерн Factory Method повністю приховав брудний код розгалуження та ізолював клієнта від процесу ініціалізації об'єктів.
- Патерни Strategy та Observer забезпечили архітектурну гнучкість: додавання нових алгоритмів або нових типів сповіщень тепер відбувається без зміни існуючих класів (виконано принцип OCP).
- Використання вбудованих подій C# дозволило досягти слабкої зв'язності (Weak Coupling) між бізнес-логікою та інфраструктурними модулями.
