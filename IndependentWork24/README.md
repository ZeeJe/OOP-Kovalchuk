# Самостійна робота №24
## Тема: Інтеграція структурних патернів + тести (підготовка до екзамену).
## Мета: Інтегрувати три структурні патерни (Composite, Decorator, Proxy) в єдиному рішенні, написати автоматизовані тести та виконати базову оцінку продуктивності й архітектурних компромісів.

## 1. Початкова ієрархія класів (з порушенням принципів проєктування)

### Опис ієрархії
Було реалізовано систему кошика покупок, де поодинокі товари (клас `SingleProduct`, що містить базову ціну) та комплексні товарні набори (клас `BundleProduct`, що містить колекцію вкладених товарів) мали абсолютно різні інтерфейси. 
Клас `BundleProduct` використовував власний специфічний метод `CalculateNestedSum()` для підрахунку вартості внутрішніх елементів. Додавання знижок вимагало створення нових класів-наслідників.

## 2. Аналіз порушення принципу LSP та проблем продуктивності
Принцип підстановки Лісков (LSP) стверджує, що об’єкти похідного класу повинні коректно замінювати об’єкти базового класу без зміни очікуваної поведінки.

У даному випадку:
- Поодинокі товари та комплекти не мали спільного базового типу поводження, тому клієнтський код був змушений будувати складні перевірки типів та приводити об'єкти до потрібного класу.
- Спроба додати сезонні знижки через наслідування призводила до "вибуху" підкласів (наприклад, `BundleWithHolidayDiscount`).
- Обчислення ціни глибоко вкладеного дерева комплектів було важкою рекурсивною операцією. Повторний виклик методу при кожному оновленні інтерфейсу сильно перевантажував систему.

Таким чином, відсутність спільного контракту ускладнювала роботу клієнта, а прямі обчислення деградували продуктивність.

## 3. Альтернативне рішення з використанням патернів
**Обраний підхід**

Було обрано підхід уніфікації об'єктів за допомогою патерну **Composite**, динамічного розширення функціоналу через **Decorator** та оптимізації обчислень за допомогою кешуючого **Proxy**.

## 4. Нова структура класів
**Опис:**

`IComponent` — загальний інтерфейс, який вводить уніфіковані методи `GetPrice()` та `GetName()` для всіх елементів.

`SingleProduct` — листок (Leaf), що представляє один товар із фіксованою вартістю. Реалізує `IComponent`.

`ProductBundle` — компонувальник (Composite), що керує колекцією `IComponent` і рекурсивно підраховує їхню загальну ціну.

`DiscountDecorator` — декоратор, який динамічно обгортає будь-яку реалізацію `IComponent` для застосування відсоткової знижки.

`CachedComponentProxy` — кешуючий заступник (Proxy), який перехоплює виклики розрахунку ціни, виконує обхід дерева лише один раз і зберігає результат у пам'яті.

## 5. Коректна робота клієнтського коду та тести
Клієнтський код тепер чітко працює лише з абстракцією `IComponent`, однаково обробляючи як один товар, так і набір із сотні товарів.

**Оцінка продуктивності:**
- Перший виклик методу (Кеш порожній) виконує повний обхід дерева і займає **~152 мс**.
- Повторний виклик (Працює Proxy) миттєво віддає результат із пам'яті за **0 мс**.

**Результати інтеграційних тестів (xUnit):**
Успішно пройдено 5 тестів, серед яких:
- Перевірка коректного підрахунку суми комплекту.
- Перевірка правильного накладання знижки декоратором.
- Перевірка стану кешу після повторного виклику (Proxy).
- Граничний сценарій: обробка порожнього набору (повертає 0).
- Негативний сценарій: викидання винятку при спробі встановити некоректну знижку (>100% або <0%).

## Висновок
- Застосування патерну Composite дозволило повністю виконати принцип LSP, уніфікувавши роботу з поодинокими та складеними об'єктами.
- Патерн Decorator надав можливість гнучко комбінувати бізнес-правила (знижки) без створення десятків нових підкласів.
- Патерн Proxy повністю усунув проблему низької продуктивності рекурсивних викликів.
- Архітектурним компромісом стала необхідність виділення додаткової пам'яті під кеш та реалізація механізму його очищення (інвалідації) при зміні даних.
