# Домашня робота №1. Виявлення God-class та принцип SRP
# 1. Характеристики "God Object" анти-патерну
God Object (або "Божественний об'єкт") — це анти-патерн програмування, який описує клас, що "знає занадто багато" або "робить занадто багато". Такий об'єкт концентрує в собі левову частку функціоналу всієї програми.

Основні характеристики:

Величезний розмір: Клас містить сотні або тисячі рядків коду.

Зайва відповідальність: Клас керує даними, логікою, відображенням та роботою з базою даних одночасно.

Низька зв'язність (Low Cohesion): Методи всередині класу логічно не пов'язані між собою.

Складність підтримки: Будь-яка зміна в одному методі може неочікувано зламати іншу частину програми.

# 2. Приклад порушення SRP (Single Responsibility Principle)
Згідно з принципом SRP, клас повинен мати лише одну причину для зміни. Розглянемо приклад класу, який керує замовленням у магазині:

public class OrderProcessor
{
    public void CreateOrder(Order order) { /* логіка створення */ }
    public void SaveToDatabase(Order order) { /* підключення до БД та збереження */ }
    public void SendConfirmationEmail(Order order) { /* логіка відправки пошти */ }
    public void PrintReceipt(Order order) { /* логіка друку чека */ }
}
## Чому це порушує SRP?
Цей клас має як мінімум чотири причини для зміни:
1. Зміна бізнес-логіки створення замовлення.
2. Зміна типу бази даних (наприклад, перехід з SQL на MongoDB).
3. Зміна поштового сервісу для відправки листів.
4. Зміна формату друку чека.

# 3. Рефакторинг для дотримання SRP
Для виправлення проблеми ми повинні розділити відповідальності між окремими класами.

## Опис реалізації після рефакторингу:
// 1. Тільки бізнес-логіка замовлення
public class OrderService
{
    public void CreateOrder(Order order) { /* ... */ }
}

// 2. Робота з базою даних
public class OrderRepository
{
    public void Save(Order order) { /* ... */ }
}

// 3. Робота з повідомленнями
public class EmailService
{
    public void SendEmail(string message) { /* ... */ }
}

// 4. Робота з друком
public class PrintService
{
    public void Print(Order order) { /* ... */ }
}
# Висновок
Рефакторинг "Божественного об'єкта" та дотримання принципу SRP дозволяє створити систему, де кожен компонент є ізольованим та незалежним. Це значно полегшує тестування, розширення функціоналу та робить код чистішим і зрозумілішим для інших розробників.
